# BWA for WebAssembly

This package builds [BWA 0.7.19](https://github.com/lh3/bwa/tree/b92993c1161e73167181558856567ef2f367e3f0)
for browsers and Node.js. It uses the upstream alignment and indexing code.
The supported release scope is `bwa index` and single-threaded `bwa mem` on
references and read sets that fit within browser memory. Other upstream
subcommands are compiled but are outside the validation scope.

## Build

On Linux, install a native C compiler, GNU Make, Python 3, curl, patch and Emscripten
3.1.64. Activate Emscripten or set `EMSDK` to its installation directory.
From the repository root:

```sh
scripts/build-bwa.sh all
```

The script accepts `native`, `patched-native` or `wasm` to build one variant.
`JOBS` sets the number of compiler processes; it does not change BWA's runtime
thread count. Sources are downloaded into `build/downloads`, checked against
[sources.lock.json](sources.lock.json), and extracted into separate build trees.
All three variants link the same pinned zlib 1.3.1 release.
`BWA_BUILD_ROOT` can select a different absolute path for the temporary build
trees; its default is `build/bwa` under the repository root.

| Variant | Output | Purpose |
| --- | --- | --- |
| Native | `build/native/bwa` | Unmodified upstream source and normal native optimizations |
| Patched native | `build/patched-native/bwa` | Port changes plus upstream scalar alignment code |
| WebAssembly | `dist/bwa/bwa.mjs`, `dist/bwa/bwa.wasm` | The same port changes compiled by Emscripten |

The module's default export is the asynchronous `createBwa` factory. `FS` and
`callMain` are exported for integration. Create a new module instance for each
invocation: BWA closes streams and retains process globals, so calling `main`
repeatedly in one instance is unsupported. Keep the `.mjs` and `.wasm` files
together, or provide Emscripten's `locateFile` option. Run browser commands in
a worker so computation does not block the page.

The repository's shared JavaScript interface handles worker execution, files
and exit codes. Ordinary BWA argument arrays are used, for example:

```js
["index", "reference.fa"]
["mem", "-t", "1", "-K", "1000000", "reference.fa", "reads_1.fastq", "reads_2.fastq"]
```

Copy the generated `.amb`, `.ann`, `.bwt`, `.pac` and `.sa` files into the next
invocation's filesystem along with the reads. Gzip-compressed FASTA/FASTQ is
handled by the pinned zlib build. Shell redirection and pipes are not BWA
arguments; the JavaScript interface captures output separately.

## Changes from upstream

[browser.patch](browser.patch) records every source change. The replacement
files are also provided individually for review:

- `kthread.c` runs every callback sequentially and processes each complete
  read/process/write pipeline batch in order. It does not discard work that
  upstream would schedule on threads.
- `kopen.c` opens local files or standard input. Network URLs and process input
  expressions are rejected explicitly. Applications can fetch a remote file
  themselves and place its bytes in the virtual filesystem.
- `bwashm.c` loads normal index files instead of POSIX shared memory. The
  `shm` command returns an error explaining that it is unavailable.
- The `-t` option accepts only `1`. The port reports an error for other values.
  Defaults remain one thread. BWA's upstream scalar SSE substitute is used
  without changes; the patched native build exercises the same code path.
- One upstream declaration of `mem_mark_primary_se` is corrected from `void`
  to `int` to match its definition. Its return value was already ignored at
  that call site. WebAssembly requires matching function signatures; the build
  treats linker warnings as errors.
- Suffix-array index serialization uses an explicit 64-bit temporary for the
  sampling interval. Upstream reads and writes eight bytes through a four-byte
  `int`, relying on native structure padding. That padding differs on wasm32.
  The correction retains the native 64-bit index file format, validates the
  loaded interval and avoids reading or overwriting the adjacent field.

The build uses a 32-bit WebAssembly address space, a growing heap capped at
2 GiB, and an 8 MiB stack. File bytes and JavaScript copies also consume memory
outside that heap. Whole-human-genome indexing is outside this release's scope.
No browser shared-memory or cross-origin-isolation configuration is needed.

## Validation

Compare the unmodified native, patched native and WebAssembly versions using
identical reference/read bytes, argument values and input order. Set `-t 1`
and the same explicit `-K` batch size for `mem`: batching can affect pairing
statistics. Check every SAM record and optional tag, not just counts or
alignment positions. Test indexes generated by each variant against the other
variants as well.

The three-way differential suite passed in Node.js 24.19.0 on 10 October 2026:

| Data | Reference | Paired reads |
| --- | --- | --- |
| Human NA12878 | 12,356 bases | 512 pairs |
| Yeast SRR1569870 | 85,779-base mitochondrial reference | 1,079 pairs |

For both datasets, all five index files were byte-identical across the native,
patched native and WebAssembly builds. All SAM records, fields and optional
tags matched for paired reads, single reads, changed seed/score parameters
(`-k 17 -T 20`), and multiple input batches (`-K 10000`). The comparator excludes
the command-line metadata in `@PG CL`; it retains secondary/supplementary
alignments and duplicate records. Cross-use of native and WebAssembly indexes,
repeated commands, empty human read files and missing-input exit status also
passed. Dataset provenance and checksums are recorded under `datasets/`.

The exact commands, binary/input hashes and case results are in
`reports/node/summary-bwa-all.json`, generated by:

```sh
node scripts/validate.mjs --tool bwa --engine node
```

These results establish equivalence for the tested inputs and options in
Node's WebAssembly engine. Browser validation in Chromium, Firefox and WebKit
is a separate CI gate; the Node report does not claim those browser tests have
passed. Other subcommands, whole genomes and arbitrary parameter combinations
remain outside the measured scope.
