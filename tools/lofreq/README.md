# LoFreq

LoFreq 2.1.5 is compiled from upstream C sources with HTSlib 1.24 and zlib 1.3.1. Its likelihood calculations, variant calling, filtering, uniqueness tests and VCF set operations run in WebAssembly. The JavaScript somatic workflow runs those core commands in sequence; it does not implement an alternate variant caller. Upstream labels this somatic workflow experimental and unfinished; this port retains that status.

Activate Emscripten 3.1.64, then run `bash scripts/build-lofreq.sh all`. The build creates the unchanged native baseline at `build/native/lofreq`, the patched native comparison at `build/patched-native/lofreq`, and `dist/lofreq/lofreq.mjs` with its `.wasm` asset. Python scripts copied beside the native executables are unchanged upstream files. They require Python 3 on the host. The build uses the C translation-unit list from upstream's Makefile and pins all dependency source archives by SHA256.

The portability patch replaces `call`'s internal shell invocation of `lofreq filter` with a direct call to the same filter function, using the same calculated thresholds and options. Parser and logging state are reset for that invocation. The native baseline retains the shell invocation for comparison.

LoFreq also depends on extended-range probabilities. Emscripten 3.1.64's default 128-bit `expl` and `log10l` implementations reduce their inputs to double precision, losing probabilities below the double range. This build links the original OpenLibm 0.8.8 `ld128` routines and their polynomial helper instead. The patched native comparison links OpenLibm's `ld80` counterparts and requires the x86 extended-precision long-double format. Compile-time checks enforce the expected formats in both builds. Coefficients and calling algorithms are unchanged. Long-double printing is enabled as well.

WebAssembly does not expose hardware floating-point exception flags. The patch records overflow, underflow and domain errors explicitly for the `exp`, `expl` and `log1p` operations used between LoFreq's numerical error checkpoints. That includes exponentials evaluated during tail summation; it does not silently remove underflow handling. LoFreq's existing minimum/maximum-probability substitutions remain unchanged. A separate `numerics.mjs` probe checks probabilities below the double range, PHRED conversion and the underflow boundary against the native implementation. This probe accompanies the calling tests.

Use the JavaScript `LoFreqRunner` for the somatic workflow. See [runtime/LOFREQ.md](../../runtime/LOFREQ.md) for its API, the single-thread restriction and `--continue` behavior. Direct invocation of the WebAssembly core with `somatic`, `call-parallel` or `vcfplot` exits with status 2 because a browser cannot launch the upstream external Python processes. There is no silent process emulation. Core commands use one worker and do not require SharedArrayBuffer or cross-origin isolation.

Multiple-testing counts in `filter` and `uniq` use signed 64-bit storage throughout parsing and correction calculations, including counts above 2,147,483,647. CLI counts must be decimal integers from 0 to 9,223,372,036,854,775,807; malformed or overflowing values are rejected. Array indices retain their upstream types and the memory limit still applies.

Files are held in memory. Local SAM/BAM, indexed BAM and reference files are supported through HTSlib; remote I/O and dynamically loaded HTSlib plugins are disabled. The compiled heap is limited to 2 GiB and practical limits depend on the browser and input size. The source still has upstream limits, including 32-bit genomic coordinates in parts of the LoFreq code. No whole-genome performance claim is made.

Validation compares unchanged native, patched native and WebAssembly results on real input reads, including complete somatic workflows. Release reports identify the exact assets, source inputs and native workflow scripts tested. Source archives can be restored from `dist/lofreq/sources/` when rebuilding a standalone package.
